# 보안

## JWT란 무엇인가

Xsolla는 로그인에 성공한 사용자에게 JWT를 발급한다. JWT에는 사용자 ID, 발급 시각, 만료 시각 같은 정보와 전자서명이 들어 있다. 백엔드는 서명을 검증하여 다음 내용을 확인한다.

- 토큰이 Xsolla에서 발급됐는가
- 토큰 내용이 전송 중 변경되지 않았는가
- 토큰이 만료되지 않았는가
- 우리 Login 프로젝트용 토큰이 맞는가

## RS256을 유지한 이유

현재 프로젝트는 처음부터 `RS256`으로 설정돼 있었으며 이를 유지했다.

- Xsolla는 **개인 키**로 JWT를 서명한다.
- 개인 키는 Xsolla 서버에만 보관된다.
- 우리 백엔드는 공개된 **JSON Web Key(JWK)**로 JWT를 검증한다.
- 검증용 공개 키가 노출되더라도 공격자가 새로운 JWT를 서명할 수 없다.
- 여러 백엔드 서비스가 검증해야 할 때도 비밀 키를 공유할 필요가 없다.

## HS256과의 차이

| 항목 | HS256 | RS256 |
|---|---|---|
| 키 구조 | 하나의 공유 비밀 키 | 개인 키와 공개 키 한 쌍 |
| 서명 | Xsolla가 공유 키로 수행 | Xsolla가 개인 키로 수행 |
| 검증 | 백엔드가 같은 공유 키 사용 | 백엔드가 공개 키 사용 |
| 키 노출 위험 | 검증 서버가 서명 가능한 비밀도 함께 가짐 | 검증 서버에는 공개 키만 존재 |
| 현재 선택 | 사용하지 않음 | 사용 |

## 변경하지 않은 설정

- **JWT 알고리즘**: `RS256`
- **토큰 수명**: `86400`초, 즉 24시간
- **JSON Web Key 재설정**: 실행하지 않음
- **OAuth 2.0 Client**: 현재 단순 Widget JWT 흐름에는 만들지 않음
- **SSO**: 여러 관련 서비스가 하나의 로그인을 공유하는 단계가 아니므로 사용하지 않음
- **MFA**: 현재 Google 소셜 로그인 학습에서는 추가하지 않음

## 키 재설정 경고창에서 취소한 이유

알고리즘을 변경하거나 키 재설정을 누르면 새로운 키가 만들어지고 이전 키는 복구할 수 없다. 이미 연결된 애플리케이션이 있으면 새 키로 모두 업데이트해야 하므로, 명확한 키 교체 계획 없이 적용하지 않는다.

## 백엔드에서 할 일

백엔드는 Xsolla가 제공하는 프로젝트의 JWKS 공개 주소에서 올바른 공개 키를 가져와 JWT의 `kid`와 서명을 검증한다. 이 작업은 프런트엔드가 아니라 백엔드에서 수행한다.

검증 시 최소한 다음 항목을 확인한다.

- 허용된 서명 알고리즘이 `RS256`인지
- 서명이 유효한지
- `exp`가 지나지 않았는지
- 발급자와 대상 프로젝트가 예상값인지
- 필요한 사용자 식별 claim이 존재하는지
